# SB08: Database Migrations (Flyway) and PostgreSQL (Testcontainers)

**Time box:** 90 min · **New concept:** versioned schema migrations, `ddl-auto: validate`, foreign keys and indexes in SQL, backfilling a new column safely, PostgreSQL, Docker Compose, Testcontainers + `@ServiceConnection`
**Review:** SB06 SQL primer, SB07 relationships, SB03 profiles and secrets

## Learning Objective
Until now, Hibernate created the tables from the entities every time the app started. That's fine for a demo, and dangerous in production: it can't migrate existing data, and nobody reviews the SQL. In real projects, **every schema change is a versioned SQL script**, checked into Git, reviewed, and applied in order by a tool. You'll write FreightBoard's schema as Flyway migrations, add a column to a table that already has data, and prove it all works on the database production would really use: PostgreSQL.

## Primer 1: migrations
```
src/main/resources/db/migration/
  V1__create_loads.sql              <- "V" + version + "__" (TWO underscores) + description
  V2__create_carriers_and_bids.sql
  V3__add_load_reference.sql
```
At start-up, Flyway compares these files with the database's `flyway_schema_history` table and runs **only the new ones**, in version order. Each applied script is recorded with a checksum.

| Rule | Why |
|---|---|
| Never edit a migration after it has run somewhere that matters | Its checksum changes, and Flyway refuses to start ("Validate failed: Migration checksum mismatch") |
| To change the schema, add `V4__...` | History is append-only, like Git commits |
| Keep Hibernate on `ddl-auto: validate` | Hibernate *checks* the tables match the entities, and never changes them |

Python analogue: **Alembic** (SQLAlchemy) or **Django migrations**. The difference is that Flyway migrations are plain SQL you write yourself, not auto-generated.

**Adding a NOT NULL column to a table with data** is a three-step dance: add it *nullable* → backfill existing rows with `UPDATE` → add `NOT NULL` (and `UNIQUE`). Try `ADD COLUMN ... NOT NULL` in one step on a table with rows, and the database rejects it, because existing rows have no value.

## Primer 2: SQL you'll need
```sql
CREATE TABLE bids (
    id       BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    load_id  BIGINT NOT NULL,
    CONSTRAINT fk_bids_load FOREIGN KEY (load_id) REFERENCES loads (id)   -- load_id must be a real loads.id
);
CREATE INDEX idx_bids_load_id ON bids (load_id);                         -- makes "WHERE load_id = ?" fast
ALTER TABLE loads ADD COLUMN reference VARCHAR(20);
UPDATE loads SET reference = 'FB-' || LPAD(CAST(id AS VARCHAR), 6, '0');
ALTER TABLE loads ALTER COLUMN reference SET NOT NULL;
ALTER TABLE loads ADD CONSTRAINT uk_loads_reference UNIQUE (reference);
```
Column names are the snake_case form of the entity fields: `weightKg` → `weight_kg`, `Bid.load` → `load_id`. Write SQL that works on **both** H2 (tests) and PostgreSQL (production). Everything above does.

## Primer 3: PostgreSQL, Docker and Testcontainers
- **Docker** runs software in isolated containers. `docker compose up -d` in this module starts a PostgreSQL defined in `compose.yaml`.
- **Testcontainers** starts a throwaway container *from a test*, and removes it afterwards. `@ServiceConnection` tells Spring Boot to connect to it, with no URLs or passwords to configure.
- Why not just H2? H2 is fast and needs nothing installed, but it isn't PostgreSQL: data types, SQL functions and locking all differ. A few tests against the real database catch what H2 hides. `PostgresIntegrationTest` is **skipped** (not failed) when Docker isn't running.

> ⚠️ **Secrets:** `application-postgres.yml` reads the password from `FREIGHTBOARD_DB_PASSWORD`, with a default that only suits a local container. Never commit a real password. Under GDPR, a production database with customer data needs its credentials in a secrets manager, and access should be limited to the people who need it.

## How to Run
From the `spring` folder:
```bash
mvn -q test -pl sb08-flyway-postgres                        # needs Docker running for the 3 PostgreSQL tests
mvn -q spring-boot:run -pl sb08-flyway-postgres             # H2, schema built by YOUR migrations
```
Against a real PostgreSQL (Docker Desktop must be running):
```bash
cd sb08-flyway-postgres && docker compose up -d && cd ..
mvn -q spring-boot:run -pl sb08-flyway-postgres -Dspring-boot.run.profiles=postgres
# ... create loads with curl, restart the app: the loads are STILL THERE this time ...
cd sb08-flyway-postgres && docker compose down && cd ..      # add -v to delete the data too
```
In the start-up log, look for Flyway's lines: `Migrating schema "public" to version "1 - create loads"` and so on. Start the app a second time: it says `Schema "public" is up to date. No migration necessary.`
